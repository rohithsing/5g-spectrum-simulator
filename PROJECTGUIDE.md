# PROJECTGUIDE.md

Complete engineering reference for the **Intelligent Spectrum Allocation for 5G/6G
Networks** testbed: what it is, how to run it, how the code is laid out, where
execution starts, how data moves, and how the two learned models are trained.

This is the implementation guide. `README.md` is the project pitch,
`METHODOLOGY.md` is the scientific argument, and this file is the map of the code.

> **Status note (read before quoting results).** The occupancy-prediction result
> is strong, reproducible and close to its information-theoretic ceiling. The
> learned *scheduler* significantly reduces harmful interference to the incumbent
> in every regime but does **not** beat the best classical scheduler on QoS
> satisfaction, and a classical scheduler given the same learned sensing
> front-end is still the strongest allocator here. See
> [§12 Current result status](#12-current-result-status) for the numbers and
> §12.4 for why the training objective and the headline KPI disagree.

## 1. What the project is

A slot-level simulator of one 5G NR downlink cell that shares a 100 MHz carrier at
3.5 GHz (band n78) with a stochastic **incumbent** (primary user), plus:

* **five classical schedulers** — Round-Robin, Proportional Fair, Max-C/I, M-LWDF,
  EXP/PF — the rules actually deployed in LTE/NR base stations;
* **two learned components** — a GRU incumbent-occupancy filter and an
  attention-based scheduling policy ("NeuroSpectrum");
* a **paired benchmark harness** with bootstrap CIs, paired Wilcoxon tests and
  Cliff's delta;
* an **information-parity contract**, enforced by tests, that guarantees the
  learned allocator sees exactly what the baselines see.

### The research question

Given *exactly the same information a real gNB scheduler has*, can a learned
allocator serve more users inside their QoS contracts and cause less harmful
interference to the incumbent than the deployed rules?

### The central design decision: information parity

The usual way a learned spectrum allocator "wins" in the literature is by being
shown the incumbent's true occupancy while the baselines only get a noisy
detector. This project forbids that structurally:

* Every allocator receives one frozen `Observation` dataclass
  (`spectrum/env.py:36`). Its fields are buffer status reports, head-of-line
  delays, 5QI parameters, **aged and quantised** CQI, and the output of **one
  shared energy detector** at a fixed `P_d = 0.85`, `P_fa = 0.12`.
* The incumbent's true state is **not a field of `Observation`**. It is consumed
  only inside the physics (`spectrum/channel.py:108`) and the collision
  accounting (`spectrum/env.py:199`).
* `tests/test_information_parity.py` asserts this mechanically, including a
  **replay test**: each allocator is fed recorded observations with no
  environment attached and must reproduce its decisions exactly. If it read
  anything else, the test fails.

### No external dataset

Everything is generated by the simulator. Every numeric constant is traceable to
a 3GPP specification or a published measurement study; the mapping is recorded in
`PARAMETER_PROVENANCE` (`spectrum/config.py:292`) and checked by
`tests/test_physics.py`.

## 3. How to run it

### Install

```bash
pip install -r requirements.txt
```

### The three commands, in order

```bash
python train.py                  # Stage 1 predictor -> Stage 2 BC + PPO  (~55 min CPU)
python evaluate.py               # paired benchmark -> results/  (~20 min)
streamlit run app.py             # interactive comparison at localhost:8501
```

Measured on CPU: behaviour cloning ~5 min (12,000 demonstration slots, 30 epochs),
PPO ~42 min (120 iterations x 1500 slots).

`evaluate.py` requires `artifacts/policy.pt`, so `train.py` must run first (it
exits with a clear message otherwise, `evaluate.py:151`).

### Useful flags

```bash
# training
python train.py --quick                   # ~4 min smoke run (4 PPO iters, 256-slot rollouts)
python train.py --skip-predictor          # reuse artifacts/predictor.pt
python train.py --skip-bc                 # reuse artifacts/policy_bc.pt, go straight to PPO
python train.py --iterations 120 --lr 1e-4 --rollout 1500 --seed 3
python train.py --bc-slots 12000 --bc-epochs 30

# evaluation
python evaluate.py --seeds 3              # quicker, wider CIs
python evaluate.py --slots 2000           # longer episodes
python evaluate.py --levels medium high   # subset of congestion regimes
python evaluate.py --no-ablations         # skip the three ablation arms

# sensitivity sweeps (no retraining; the frozen artifacts are re-evaluated)
python sensitivity.py --seeds 4 --congestion high --slots 800

# tests
python -m pytest tests/ -q                # 52 tests, ~15 s
```

### Docker

```bash
docker build -t spectrum-sim .
docker run -p 8501:8501 spectrum-sim
```

### The two sides and the one interface

The architecture has exactly one seam: **`Observation` in, `assignment` out.**

* **Environment side** (`env`, `channel`, `traffic`, `incumbent`, `metrics`)
  owns all ground truth and all physics.
* **Allocator side** (`baselines`, `agent`, `policy`, `predictor`) sees only an
  `Observation` and returns an `(n_rbg,)` integer array.

Everything else in the project — the fairness argument, the ablations, the replay
test — is a consequence of that seam being the only channel between the two sides.

### Radio numerology (`spectrum/config.py:170`)

| Quantity | Value | Provenance |
|---|---|---|
| Carrier / bandwidth / SCS | 3.5 GHz / 100 MHz / 30 kHz | TS 38.104 FR1 band n78 |
| Slot duration | 0.5 ms (`1 ms / 2^mu`, mu=1) | NR numerology |
| RBGs | 18 (273 PRB, RBG size 16) | TS 38.214 Table 5.1.2.2.1-1 |
| Incumbent subbands | 6 (3 RBGs each) | — |
| BS EIRP | 46 dBm | TS 38.104 wide-area BS class |
| Cell radius | 350 m, UEs 35–350 m | TR 38.901 UMa |
| Path loss | UMa NLOS, 5 dB log-normal shadowing | TR 38.901 eq. 7.4.1-1, Table 7.5-6 |
| CQI -> rate | table 2, 10 % BLER | TS 38.214 Table 5.2.2.1-3 |
| CQI report | 2 slots old, period 4 slots, 1 dB error | — (equal for all allocators) |
| HARQ | 3 retx, 2.5 dB chase-combining gain | TS 38.321 |
| 5QI bearers | 82 URLLC, 1 VoIP, 2 video, 9 best-effort | TS 23.501 Table 5.7.4-1 |
| Incumbent | 2-state semi-Markov, mean ON 42 slots | Saleem & Rehmani (2014) |
| Detector | `P_d = 0.85`, `P_fa = 0.12` | FCC 47 CFR Part 96 |

### Congestion regimes (`spectrum/config.py:158`)

Regimes scale **offered load, not the scheduler's resources**, so every allocator
is stressed identically.

| Regime | Load x | UEs | Incumbent duty cycle |
|---|---|---|---|
| `low` | 0.55 | 20 | 12 % |
| `medium` | 1.00 | 35 | 22 % |
| `high` | 1.60 | 55 | 34 % |
| `peak` | 2.30 | 80 | 46 % |

### 6.3 One slot, in full detail — `SpectrumEnv.step`

This is the innermost loop of the whole project (`spectrum/env.py:151`).

```
  allocator.allocate(obs) -> assignment: (n_rbg,) int, -1 = mute
         |
         v
  env.step(assignment)                                        env.py:151
   1. validate: no index >= n_ue                                  :159
   2. truth = incumbent.active                 <- GROUND TRUTH enters here, and
                                                 ONLY here                :162
   3. channel.transmit(assignment, truth, harq_retx)          channel.py:159
        sinr   = true_sinr_db(truth)      <- incumbent raises the noise floor
        required = CQI_SINR_THRESHOLDS_DB[reported_cqi]
                                          <- MCS from the AGED report, so an
                                            optimistic report really fails
        eff_sinr = sinr + 2.5 dB * harq_retx_count   (chase combining)
        bler   = logistic(eff_sinr - required)       channel.py:233
        success = rng.random() >= bler
        -> delivered_bits, acked, collided
   4. per-RBG delivered bits -> per-UE totals                      :170
   5. traffic.serve(ue, bits, slot)                           traffic.py:89
        drain the queue oldest-packet-first; return bits ACTUALLY consumed
        -> the shortfall is "allocation waste" (over-allocation)
   6. HARQ bookkeeping: reset on any ACK, else increment to max 3   :178
   7. traffic.expire(slot)                                   traffic.py:113
        drop packets past their delay budget. ** Dropping is what makes the
```

## 8. API architecture

**There is no network API.** No REST, no gRPC, no WebSocket, no database. The
"API" of this project is a set of Python contracts. Four of them matter.

### 8.1 The allocator contract — `spectrum/baselines.py:39`

```python
class Allocator:
    name: str          # full name, used in every table and plot
    short_name: str    # compact label for plots

    def reset(self, cfg: SimConfig) -> None:
        """Called once per episode, before the first allocate()."""
        self.cfg = cfg

    def allocate(self, obs: Observation) -> np.ndarray:
        """Return an (n_rbg,) int array of UE indices, or -1 to mute."""
        raise NotImplementedError
```

This is the entire extension point. Anything implementing these two methods
drops into `run_episode`, `evaluate.py`, `sensitivity.py` and the dashboard with
no further work. Implementations: five classical schedulers,
`NeuroSpectrumAllocator`, `PredictorAugmentedBaseline`.

**The hard rule:** `allocate` may read *only* `obs`, and must be a pure function
of the observation stream. `tests/test_information_parity.py` enforces this by
replaying recorded observations with no environment attached and asserting the
decisions are identical.

### 8.2 The environment contract — `spectrum/env.py:75`

Gym-like, but deliberately **not** a `gym.Env` (no dependency, and the action
space is a structured assignment rather than a flat `Discrete`):

```python
env = SpectrumEnv(cfg, seed=seed)
obs  = env.reset(seed)            # -> Observation
obs  = env.observe()              # -> Observation, no side effects
obs, reward, done, info = env.step(assignment)
summary = env.episode_summary()   # -> Dict[str, float], the KPI record
```

`info` carries `useful_bits`, `delivered_bits`, `collisions`, `completed`,
`expired`, `jain`, `qos_fraction`, `reward_terms`, and `_truth_incumbent`. The
leading underscore marks the one key that is ground truth; it is returned
**strictly after** the decision and is used only for evaluation and predictor
supervision.

### 8.3 The occupancy-estimator contract — `spectrum/predictor.py`

```python
class <Estimator>:
    name: str
    def reset(self, n_subbands: int) -> None: ...
    def probability(self, decision: np.ndarray, energy: np.ndarray) -> np.ndarray:
        """-> (n_subbands,) float in [0, 1]"""
```

Satisfied by `EnergyDetector` (memoryless, returns the hard bit), `BayesFilter`
(exact HMM forward filter, needs the true model — an upper bound, not deployable)
and `GRUPredictor` (learned, infers everything from data). All three consume
**exactly the same input**, so substituting one for another cannot break
information parity.

`OccupancyEstimator` (`predictor.py:142`) wraps any of them with a one-slot cache.
This matters because `GRUPredictor` is a *filter*: every `probability()` call
advances its hidden state. Several components want the estimate for the same slot
(the feature extractor, the mute head, a predictor-augmented baseline), and
calling through twice would advance the filter twice and feed it the same
observation more than once.

### 8.4 The runner contract — `spectrum/runner.py:14`

```python
run_episode(allocator, cfg, seed,
            collect_sensing_trace=False,   # adds result["_sensing"]
            collect_timeline=False)        # adds result["_timeline"]
    -> Dict[str, Any]   # KPI summary + total_reward, allocator, congestion, seed

run_suite(allocator, congestion_levels, seeds, base_cfg=None)
    -> List[Dict[str, Any]]
```

One loop, used by training, evaluation, the sensitivity sweeps and the dashboard.
Keeping it single-sourced is why the training objective and the reported numbers
cannot drift apart.

### 9.1 The reward function — `spectrum/env.py:261`

| Term | Formula | Weight |
|---|---|---|
| `goodput` | `useful_bits / max_bits` | +1.5 |
| `completed` | `packets_completed / lambda` | +1.5 |
| `dropped` | `-packets_expired / lambda` | +3.0 |
| `fairness` | Jain index | +0.4 |
| `collision` | `-n_collisions / n_rbg` | +2.0 |
| `waste` | `-(delivered - useful) / max_bits` | +0.5 |
| `vacancy` | `-wasted_vacancies / idle_rbg_count` | +0.3 |

`lambda` is the cell's known mean packet-arrival rate, so `completed` and
`dropped` are on the same, load-independent scale and **dropping a packet always
costs more than delivering one gains** (3.0 > 1.5).

**Why QoS is scored by packet outcomes and not by queue state.** The obvious
proxy — "fraction of UEs currently inside their delay budget" — is *gameable in
this simulator*, because expiry removes a packet from the queue. Head-of-line
delay therefore **resets when a deadline is missed**, so an allocator that
transmits nothing keeps that statistic near 1.0 while dropping every packet.
Rewarding it produced exactly that degenerate policy. The metric is still
computed, as `_instantaneous_qos` (`env.py:311`), but it is reported for
monitoring only and deliberately excluded from the reward.

### 9.2 Three non-obvious training fixes

These are the things that made the system trainable at all, and each is recorded
in the source with the measurement that motivated it.

**(a) Learned logit temperature** — `policy.py:184`

```python
self.log_scale = nn.Parameter(torch.tensor(1.6))
```

The quantity a good scheduler ranks on (`urgency x rate / mean_rate`) spans ten
or more nats, but the heads read LayerNorm'd features and emit roughly unit-scale
values. Without a learned temperature the softmax can never become peaked enough
to express a decisive ranking.

**(b) Per-sub-action PPO clipping** — `ppo.py:113`

A slot's action is 18 sequential categorical choices. Summing their
log-probabilities gives the correct joint, but feeding that joint to PPO's ratio
is a trap: the ratio becomes a *product* of 18 per-decision ratios, so a 0.05
shift in each inflates it to `e^0.9 ~ 2.5` and the clip zeroes the gradient.
Measured here, the joint form held `clip_frac` at 0.5–0.64 while the true
per-decision KL was only 0.004, and learning stalled. `masked_log_probs`
therefore returns `(B, n_rbg)` **unreduced**, and each sub-action is clipped on
its own ratio against the shared slot advantage.

**(c) KL anchor to the cloned policy** — `ppo.py:61`, `ppo.py:311`

One scalar advantage per slot has to shape 18 decisions over ~80 candidates each,
so the gradient is noisy. Without an anchor the policy drifts away from a good
initialisation faster than it finds genuine improvements: measured without it,
goodput fell from 184 to 28 Mb/s over 12 iterations while the agent rediscovered
"mute everything". The anchor is annealed — strong early, when the value function
is poor and the advantage is mostly noise, then relaxed.

**The floor matters as much as the schedule.** Annealing to 0.1 rather than ~0
meant the anchor never actually released, and combined with `target_kl = 0.015`
(which early-stopped 27.5 % of updates) it pinned the policy to its clone: over
40 iterations the reward slope was +0.0017/iter against a standard error of
0.0013, i.e. `t = 1.31` — no measurable learning. The guard that prevents
collapse had become the thing preventing improvement. Current values are
`bc_kl_final = 0.01` and `target_kl = 0.03`.

**(d) Imitation fidelity is the binding constraint** — `bc.py:121`

PPO is anchored to the clone, so whatever the clone fails to reproduce is a
ceiling RL starts *below* and cannot climb past. With a flat learning rate over
12 epochs the clone reached only 66.4 % teacher-match and scored 1.5146
reward/slot against the teacher's 1.5935 — and the PPO policy trained from it
scored 1.4750, i.e. *below its own starting point*. Cosine-annealing the learning
rate over 30 epochs on 12,000 slots raised the match to 77.1 %, which recovered
almost the whole KPI gap to the teacher (QoS 44.3 -> 48.9 %, goodput
157 -> 168 Mb/s) and gave PPO a launchpad it could actually improve on.

This is underfitting, not a capacity limit, and that is checkable rather than
assumed: the factored logit `score_u + gain_u * z_uk` represents M-LWDF's
`log(urgency_u / R_u) + log(bits_uk)` exactly when `gain_u` is constant. Setting
those weights analytically and replaying them through the decoder's own mask
reproduces the teacher on **96.4 %** of per-RBG decisions. So ~19 points of pure
optimisation headroom remain in the clone.

**(e) Do not select checkpoints on the training reward** — `train.py:156`

Per-rollout mean reward has `sigma ~ 0.12` here, so the maximum over ~120
iterations is worth roughly `+2 sigma` from selection alone — comparable to the
entire apparent gain of any "best" iterate. Two schemes were tried and both
mined noise rather than signal:

* best 3-iteration smoothed reward -> shipped a checkpoint **worse** than the
  final iterate on held-out seeds (46.4 % vs 47.2 % QoS satisfaction);
* best of {clone, final iterate} on 12 held-out episodes -> preferred the clone
  (44.95 % vs 42.75 %), a verdict that **reversed** on the 32-episode benchmark
  (46.71 % vs 47.37 %).

`policy.pt` is therefore the final iterate, unconditionally, and RL's
contribution is measured where it can actually be seen: `evaluate.py` carries the
clone as an ablation arm and the two are compared with a paired Wilcoxon test
over the full benchmark (§12.3). The lesson generalises past this project — if a
selection criterion is noisier than the effect it is selecting on, it is a random
number generator with extra steps.

### 9.3 What a reward/slot number means

PPO's reward is an arbitrary weighted sum, so `1.6 reward/slot` is
uninterpretable on its own and a flat training curve cannot be read as failure
without knowing the scale. Measured on PPO's own training distribution
(regimes medium/high/peak, 500-slot episodes, 3 seeds):

| Allocator | reward/slot |
|---|---|
| Max-C/I | +0.4385 |
| Round-Robin | +0.9721 |
| Proportional Fair | +1.2864 |
| M-LWDF | +1.4588 |
| EXP/PF | +1.4937 |
| **M-LWDF + learned sensing** (best heuristic) | **+1.5935** |
| BC clone, 77 % match (PPO's starting point) | +1.5146 |

Two things follow. First, Max-C/I scores lowest despite having the **highest raw
goodput** of any allocator — the reward is correctly charging it for the packets
it drops and the collisions it causes, so the weights are not obviously
mis-specified. Second, a PPO run sitting at ~1.6–1.7 is above the best heuristic
rather than stuck, even when its slope over iterations is flat: on the current
configuration the policy gains most of its improvement over the clone within the
first iteration and then plateaus, so slope alone is a misleading diagnostic.
Reproduce this table before concluding anything from a training curve.

### 9.4 Why the BC teacher uses the learned estimate

`build_teacher` (`bc.py:192`) returns `PredictorAugmentedBaseline(MLWDF(),
predictor)`, not plain `MLWDF()`. This detail is load-bearing. Plain M-LWDF mutes
exactly when `sensing_decision == 1`, so a student cloning it learns that the
hard bit predicts the teacher perfectly and that `p_busy` can be ignored — and
then inherits the classical detector's collision rate despite having a far better
estimate sitting in its own input. Switching the teacher cut the clone's collision
rate by 2.4–3.6x (peak: 11.5 % -> 3.2 %).

### 11.4 Factorised logits + learned temperature — `spectrum/policy.py:213`

Scoring all `n_ue x n_rbg` pairs jointly would be expensive. Instead each UE
emits a priority `score_u` and a channel sensitivity `gain_u`:

```python
score = self.score_head(h).squeeze(-1)              # (B, MAX_UE)
gain = F.softplus(self.gain_head(h)).squeeze(-1)    # (B, MAX_UE)

# logits[b, k, u] = scale * (score[b, u] + gain[b, u] * z[b, u, k])
scale = F.softplus(self.log_scale)
pair = scale * (score.unsqueeze(-1) + gain.unsqueeze(-1) * z)  # (B, MAX_UE, n_rbg)
pair = pair.transpose(1, 2)                                     # (B, n_rbg, MAX_UE)

mute = scale * self.mute_head(torch.cat([rbg, glob_rep], dim=-1))
logits = torch.cat([pair, mute], dim=-1)             # (B, n_rbg, MAX_UE + 1)
```

Rank-2 in the pair space, but still lets different UEs prefer different parts of
the band — which is the part that matters. The `mute` column is where the learned
occupancy estimate enters the scheduling decision: `rbg` carries `p_busy` as its
first feature (`policy.py:112`).

### 11.7 The Bayes-optimal ceiling — `spectrum/predictor.py:81`

What turns "our network is better" into "our network captures ~98 % of what is
recoverable":

```python
def probability(self, decision, energy):
    # Predict: propagate the prior through the chain.
    prior = self.belief * self.transition[1, 1] + (1.0 - self.belief) * self.transition[0, 1]
    # Update: Gaussian likelihoods N(0,1) under H0 and N(mu,1) under H1.
    llr = self.mu_h1 * energy - 0.5 * self.mu_h1 ** 2
    odds = (prior / np.maximum(1.0 - prior, 1e-12)) * np.exp(np.clip(llr, -30.0, 30.0))
    self.belief = np.clip(odds / (1.0 + odds), 1e-6, 1.0 - 1e-6)
    return self.belief.copy()
```

### 11.8 The slot-cached filter — `spectrum/predictor.py:168`

A subtle correctness fix. `GRUPredictor` is a filter, so a second call in the
same slot would advance the hidden state twice and feed it one observation twice:

```python
def __call__(self, obs) -> np.ndarray:
    if self._slot == obs.slot and self._value is not None:
        return self._value
    if self.predictor is None:
        value = obs.sensing_decision.astype(np.float64)
    else:
        value = self.predictor.probability(obs.sensing_decision, obs.sensing_energy)
    self._slot = obs.slot
    self._value = value
    return value
```

### 12.1 Occupancy estimation — the strong result

| Estimator | Accuracy | Precision | Recall | F1 | AUC | Miss rate | False-alarm rate |

This result is real, and the Bayes row is what makes it rigorous. The two error

essentially no headroom left** — a request to "improve accuracy and precision"
cannot be met by a better architecture, because the remaining gap is irreducible
uncertainty in the sensing stream itself. See §14.2 for what *would* move it.

### 12.4 The reward is not the KPI

Worth stating plainly, because it misled this project twice. PPO optimises its
reward successfully: reward/slot rises from the clone's **1.5146** to
**1.6-1.74**, well past the best heuristic's 1.5935 (§9.3). That gain converts
into **+0.65 pp of QoS satisfaction, p = 0.269**.

The reason is structural, not a tuning problem. The reward sums packet outcomes
over the cell, while `qos_satisfaction_pct` counts UEs meeting a **two-sided
per-UE contract** (>= 90 % of offered bits delivered **and** >= 95 % of packets
inside the budget, `metrics.py:136`). An allocator can serve more packets in
aggregate while pushing more individual UEs below their thresholds. Optimising a
cell-aggregate utility is simply not the same problem as maximising the count of
satisfied contracts.

This also kills the obvious first guess — that the `collision` weight of 2.0
against `goodput` 1.5 forces a bad trade. It does not: the clone achieves low
collisions *and* high goodput together. The misalignment is between aggregate and
per-UE accounting, not between two of the weights.

### 12.5 What this means for a paper

The methodology, the simulator and the predictor are publication-grade. The
original headline claim — that a learned allocator beats the deployed schedulers
on QoS — is **not supported** and has been removed from `README.md`.

The defensible paper is: **learned incumbent-occupancy filtering for spectrum
sharing under enforced information parity.** Its contributions are the GRU filter
benchmarked against a Bayes-optimal ceiling (§12.1), the mechanically enforced
parity contract including the replay test (§13), a 50-72 % reduction in harmful
interference to the incumbent at every load (§12.2), and a clean component
decomposition showing the gain is attributable to sensing rather than to the
learned scheduler (§12.3).

Reported alongside it, honestly: a strong classical scheduler given the same
learned front-end is still the best allocator in this testbed, and PPO on top of
a well-fitted behaviour clone buys one metric out of seven. The reward-vs-KPI
analysis in §12.4 and the credit-assignment result in §9.2b are the kind of
negative findings that are genuinely useful to the next person who tries this.

## 14. Extending the project

### 14.1 The RL stage: what has been tried, and what is left

Five hyper-parameter and plumbing problems were diagnosed and fixed. All of them
were real, and together they moved the proposed system from 45.83 % to 47.37 %
QoS and from 160.5 to 169.5 Mb/s goodput. **None of them made RL the source of
the result**, and the remaining item is not a hyper-parameter.

Done:

1. ~~**Anneal `bc_coef` to 0, not 0.1**~~ (`ppo.py:70`) — the anchor never
   released. Now `bc_kl_final = 0.01`.
2. ~~**Raise `target_kl`**~~ (`ppo.py:54`) — `0.015` early-stopped 27.5 % of
   updates. Now `0.03`.
3. ~~**More iterations**~~ — 40 was far too few. Now 120 by default.
4. ~~**Fix the learning rate**~~ — `3e-4` had been tuned against the throttle in
   (2); once released it overshot badly (`KL 0.705`, entropy collapsing
   1.38 -> 0.79 in one update). Now `1e-4`.
5. ~~**Fix imitation fidelity**~~ — the real bottleneck, and not on the original
   list. See §9.2d: 66.4 % -> 77.1 % teacher-match.

Also settled, so nobody repeats it: **the reward weights are not the problem.**
`collision` at 2.0 against `goodput` at 1.5 does not force a bad trade — the
behaviour clone achieves 2.58 % collisions *and* 164 Mb/s simultaneously. That
hypothesis is dead.

What is actually left, in priority order:

1. **Make the reward match the KPI** (`env.py:261`). This is now the live issue
   and §12.4 is the evidence: PPO raises reward/slot from 1.5146 to 1.6-1.74 and
   buys +0.65 pp of QoS satisfaction at `p = 0.269`. The reward is a cell
   aggregate; the KPI counts UEs meeting a two-sided per-UE contract. Score the
   contract instead — e.g. reward the *change* in the number of UEs projected to
   satisfy both halves of their 5QI contract, or weight each UE's packet outcomes
   by how close that UE is to its threshold. Until the objective and the KPI
   agree, better RL cannot help, and a flat QoS curve is the correct outcome
   rather than a bug.
2. **Credit assignment** (`ppo.py:299`). One scalar advantage per slot still has
   to shape 18 sub-actions. `channel.transmit` already returns per-RBG
   `delivered` and `collided`, so the attributable part of the reward can be
   pushed down to the sub-action that caused it; the slot-level terms
   (`completed`, `dropped`, `fairness`, `vacancy`) stay shared. This is the
   principled fix and it has not been attempted.
3. **Close the remaining BC gap.** 77.1 % teacher-match against a verified
   ~96.4 % architectural ceiling (§9.2d) leaves ~19 pp on the table, and the
   clone is both PPO's starting point and its KL anchor. More epochs, a larger
   demonstration set, or initialising `score`/`gain` from the analytic solution
   are all cheap to try.
4. **Fix the low-load over-muting.** Wasted vacancy at 12 % duty cycle is
   -86.6 % against Round-Robin (§12.2) — by far the worst number in the study.
   The mute head is too conservative when the incumbent is mostly idle; the
   `vacancy` reward weight of 0.3 is a candidate, as is feeding the mute head
   the predicted duty cycle.

A note on methodology for whoever continues this. **Do not select checkpoints on
the training reward here.** Per-rollout reward has `sigma ~ 0.12`, so the best of
~120 iterations is worth about `+2 sigma` from selection alone. Both attempts at
being clever about this failed: best-3-iteration-smoothed reward shipped a
checkpoint *worse* than the final iterate on held-out seeds, and choosing between
the clone and the final iterate on 12 held-out episodes gave a verdict that
reversed on the 32-episode benchmark. `train.py` therefore ships the final
iterate unconditionally and `evaluate.py` carries the clone as an ablation arm so
the comparison is made with a paired test over the full benchmark.

### 14.2 Where the predictor could still gain

Accuracy is at the Bayes ceiling for *this* incumbent model, so improvement
requires changing the problem, not the architecture:

* **Multi-step-ahead prediction.** Current output is a filtered estimate of
  occupancy *now*. Forecasting 2–10 slots ahead is strictly harder, is what a
  scheduler actually needs (the CQI report is already 2 slots stale), and has real
  headroom. The `BayesFilter` extends to it directly, so the upper bound comes
  along for free.
* **Cross-subband correlation.** The GRU is applied per subband independently.
  Real incumbents occupy adjacent channels together; a model over the
  `(n_subbands,)` vector could exploit that. Requires making `IncumbentProcess`
  correlate subbands first.
* **Structured incumbents.** Radar and satellite have periodic duty cycles that
  are *easier* to predict than a geometric-sojourn Markov chain — which is why
  the README calls the current result conservative. A periodic or semi-Markov
  incumbent with non-geometric sojourns would both raise the achievable number
  and break the `BayesFilter`'s optimality, which is itself interesting.
* **Detector-quality sweep.** `sensitivity.py` already does this. If the gain
  survives a better detector, that is a stronger claim than the headline.

### 14.3 Adding an allocator

Subclass `Allocator`, implement `reset` and `allocate`, add it to
`build_classical()` (`baselines.py:242`) or `build_allocators()`
(`evaluate.py:145`). It then appears in every table, plot and dashboard tab
automatically. `tests/test_allocators.py` will check the contract; keep
`allocate` a pure function of `obs` or `test_information_parity.py` will fail.

### 14.4 Known limitations (from `README.md`, all accurate)

* Single cell. Inter-cell interference is a static floor, not a second scheduler
  reacting to this one.
* Single antenna port. No MIMO, no beamforming, no spatial multiplexing.
* The incumbent is a two-state Markov process.
* The Bayes-optimal reference is only optimal for *this* incumbent model.
* Results are simulator-internal.

To which this guide adds:

* **The learned scheduler does not beat the best classical scheduler on QoS.**
  `M-LWDF + learned sensing` remains the strongest allocator in this testbed.
  See §12.3.
* **RL's measurable contribution is one metric out of seven** — deadline misses,
  `p = 0.011`. See §12.3.
* **The training objective is not the reported KPI**, and that is a property of
  the reward's design rather than of the optimiser. See §12.4.
* `results/` was generated by the artifacts currently in the tree. Both are
  committed together, so any later retraining must regenerate both or the two
  will silently disagree.
